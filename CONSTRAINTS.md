# ВСК ДМС-ассистент Qwen Release — Ограничения

Документ фиксирует текущие технические ограничения production-версии.

---

## Обработка запросов

**Синхронный блокирующий эндпоинт.**
`POST /api/update` не возвращает ответ до полной обработки файла.
Время обработки зависит от размера документа и количества чанков.
> Для масштабирования потребуется очередь задач (Celery, ARQ) и асинхронный статус-эндпоинт.

**Один запрос одновременно.**
Нет воркеров, нет пула. Второй запрос ждёт завершения первого.

**Нет повторной обработки при сбое.**
Если LLM вернул неустранимую ошибку на одном из чанков — весь запрос падает с 500. Частичный результат не сохраняется в Excel.

---

## LLM и качество

**Качество зависит от промта.**
Система отправляет нормативную базу + требования клиента. QwenModel парсит таблицу по шаблону, который задан в `AI_PROMPT_TEMPLATE`.

**Сопоставление строк — эвристическое, не семантическое.**
`ExcelReportWriter` ищет строку в исходном файле по четырём уровням:
1. Точное совпадение
2. Совпадение суффикса (с разделителем)
3. Совпадение префикса
4. Jaccard-перекрытие слов ≥ 75% с ограничением соотношения длин 3:1

Парафразы и синонимы могут не совпасть — строка останется без аннотации.

**RAG по ключевым словам (Jaccard), не семантический.**
`NormativeIndex` сопоставляет разделы базы с чанком по пересечению слов. Синонимы и парафразы не учитываются. При `LLM_MAX_SECTIONS=10` в промт попадают только 10 разделов — остальные игнорируются.

**Нормативная база перечитывается при каждом запросе.**
Файл читается с диска и индексируется заново при каждом вызове `POST /api/update`. При очень большой базе (>1 МБ) это заметная лишняя работа.
> Для production — кэшировать `NormativeIndex` на уровне приложения с инвалидацией по mtime файла.

**Лимиты API обрабатываются автоматически.**
При получении ошибки 503 (перегрузка) система повторяет запрос до 3 раз с паузой 5 секунд. При пустом ответе повторяет до 3 раз с паузой 1 секунда.

---

## Входные данные

**PDF — только текстовый, не сканы.**
Сканированные PDF (изображения) не читаются. Нужен OCR — в текущей версии не реализован.

**Структура таблицы не валидируется.**
Система ожидает, что требования клиента — это строки таблицы или нумерованные пункты. Произвольный текст без структуры может привести к некорректной разбивке на чанки.

**Файл клиента передаётся как путь внутри контейнера.**
API принимает `file_path` — путь к файлу внутри контейнера. Загрузка файла через HTTP multipart не поддерживается.

**Переводы строк в ячейках Excel обрабатываются.**
Символ `\n` внутри ячеек Excel заменяется на пробел при парсинге. Исходное форматирование ячейки (многострочность) в выходном файле не восстанавливается.

---

## Нормативная база

**Несколько файлов в директории конкатенируются.**
`NormativeBaseLoader` читает все файлы из `NORMATIVE_BASE`-директории и объединяет их в один текст. Если при обновлении базы старый файл не удалить, оба попадут в промт одновременно.

**Нет версионирования базы.**
Нет истории изменений нормативных документов. Неизвестно, по какой версии базы был сформирован конкретный ответ.

**Большие базы могут не влезть в контекст.**
Если нормативная база превышает выделенный лимит токенов, система автоматически отбирает наиболее релевантные разделы (по Jaccard). Остальные разделы игнорируются. В логах выводится информация с числом отобранных разделов.

---

## Безопасность и доступ

**Нет аутентификации.**
Любой, кто имеет доступ к порту 8001, может отправить запрос.

**Нет валидации пути к файлу.**
`file_path` в запросе не проверяется на path traversal. В production обязательна санитизация.

**API-ключи отсутствуют.**
Qwen API-адрес и учётные данные передаются через переменные окружения в `.env`.

---

## Выходные данные

**Выходной файл перезаписывается.**
При повторной обработке `client_ответ.xlsx` перезаписывается без предупреждения.

**Для PDF и неизвестных форматов — fallback на .docx.**
Оригинальная структура PDF не сохраняется — ответ создаётся как новый Word-документ.

**Debug-файлы пишутся рядом с исходником.**
`*_llm_debug.md` и `*_llm_output.json` создаются в той же папке, что и исходный файл. Нет ротации, накапливаются на диске. JSON для большого документа (62 чанка) занимает несколько МБ.

**Объединённые ячейки обрабатываются частично.**
Аннотации записываются только в незаблокированные ячейки. Ячейки, входящие в merged range (кроме верхней левой), пропускаются без предупреждения.

---

## Инфраструктура

**Нет мониторинга и алертов.**
Логи только в stdout контейнера. Нет метрик, нет трейсинга запросов.

**Нет истории обработки.**
Каждый запрос независим. JSON-кэш (`*_llm_output.json`) — единственное хранилище результата.

**Один инстанс, нет горизонтального масштабирования.**
Docker Compose, один контейнер API.

## Сверка деклараций с ген. полисом (`POST /api/reconcile`)

Второй пайплайн (`document_assistant/cargo/`) — не отдельная копия оркестрации: каждый вызов ИИ (извлечение пунктов из документа полиса/ДС в `RulesMatrixBuilder`, сверка одной декларации в `CargoReconciliationService`) выполняется через тот же `AIAssistantService`, что и ДМС-пайплайн, только с cargo-специфичными preprocessor/postprocessor/report_export. Отсюда два следствия:

- **Частичные результаты при сбое чанка теперь общие с ДМС.** Если чанк (строка мультистрочной декларации или часть документа полиса/ДС) не прошёл 3 попытки, `AIAssistantService` пропускает его и продолжает — как и в ДМС-пайплайне. Для мультистрочной декларации это значит, что «строка 2» может отсутствовать в результате, а «строка 3» получит корректную метку `200/3` (не `200/2`) — `ReconciliationPostProcessor` получает настоящий номер чанка от `AIAssistantService`, а не считает вызовы сам.
- **Debug/JSON-кэш пишется и для документов полиса/ДС.** `_llm_debug.md`/`_llm_output.json` теперь создаются рядом с КАЖДЫМ файлом ген.полиса/ДС при построении матрицы (не только рядом с декларацией) — расширяет уже описанную ниже проблему накопления debug-файлов на папку полиса.

Большая часть ограничений выше на этот пайплайн распространяется без изменений (синхронный блокирующий эндпоинт, один запрос одновременно, нет аутентификации, нет проверки path traversal на `policy_folder`/`declaration_paths`/`special_conditions_path`, debug/кэш-файлы не ротируются, выходной файл перезаписывается без предупреждения). Специфичные для этого пайплайна ограничения:

**Различение ген.полиса и ДС — по имени файла, не по содержимому.**
`PolicyFilenameParser`/`DeclarationFilenameParser` (`document_assistant/cargo/filename_parsing.py`) — эвристики по регулярным выражениям, подобранные без образцов реальных файлов заказчика. Нестандартное имя файла (без «ДС №N» / «Ген. полис» в названии, номер декларации не в виде отдельного числа) не будет распознано — вернётся `None`/`"UNKNOWN"`, файл выпадет из матрицы или получит номер `UNKNOWN`. Требует донастройки regex под реальную номенклатуру файлов до продакшна.

**Слияние пунктов при сборке матрицы — нечёткое сопоставление текста, не семантическое.**
`ClauseMerger` группирует пункты между документами по нормализованному тексту (точное совпадение → префикс → пересечение слов ≥ 75%), тем же приёмом, что `ExcelReportWriter._find_row_global` в ДМС-пайплайне. Если LLM по-разному сформулирует один и тот же пункт в разных ДС, слияние может создать два раздельных пункта вместо одного — тогда «побеждает последний ДС» не сработает для этого пункта.

**Приоритет ДС строится по порядку обработки, а не по проверке дат в рантайме.**
`ClauseMerger.merge()` доверяет порядку входных источников (полис → ДС по возрастанию `(valid_from, ds_number)`) — сам не сравнивает даты повторно. Если `PolicyFolderScanner` получит источники в неверном порядке (например, `valid_from` не распознан из имени файла), самый поздний по факту ДС не обязательно победит.

**Тип декларации определяется по наличию markdown-таблицы.**
`DeclarationTypeClassifier` считает декларацию мультистрочной при 2+ строках таблицы; декларация без табличной структуры (сплошной текст, повторяющиеся блоки в Word без таблицы) всегда классифицируется как однострочная — сценарий с несколькими перевозками в свободном тексте не поддерживается.

**Месячная папка «Декларации/{месяц}» — только предупреждение, не перемещение файлов.**
`PeriodMonthResolver` в v1 не заполняется (нет извлечения даты начала периода страхования из декларации) — поле `warnings` в ответе `/api/reconcile` всегда пустое. Результат сохраняется рядом с исходным файлом декларации, а не в вычисленной по дате месячной папке.

**Нет образцов реальных данных для обкатки промптов.**
`RECONCILIATION_RULES_BASE`, `MATRIX_PROMPT_TEMPLATE`, `RECONCILIATION_PROMPT_TEMPLATE` не проверялись на реальных ген.полисах/ДС/декларациях — только на синтетических данных в юнит- и smoke-тестах.
